# PR2PAY

**Verify code contributions. Approve the reward. Send it through PayPal.**

PR2PAY is a local-first moderator dashboard for one GitHub repository. It imports task Issues, reads Pull Requests and diffs, asks OpenAI to evaluate the PR against the Issue's acceptance criteria, and lets a human moderator authorize a PayPal Payouts request.

It is deliberately narrow for a seven-day hackathon. It does not manage organizations or multiple repositories, and it does not write to GitHub.

## What is implemented

- One configured GitHub repository, prefilled with `https://github.com/shubhigupta795-lab/STUDYMATE/tree/latest_version`.
- Read-only GitHub REST API integration for repository verification, open Issues, PR details, changed-file patches, commit SHA and available CI check runs.
- GitHub Issue import with a fixed reward line and explicit acceptance checklist.
- OpenAI structured-output evaluation, evidence per criterion, confidence, risk notes and an equal-weight score computed by the backend.
- Eligibility at **60% or above**. Inconclusive criteria do not count as passed.
- Commit-SHA snapshot and freshness checks before moderator approval and before payout.
- Separate moderator approval and final payment-confirmation actions.
- PayPal OAuth 2.0 Client Credentials, Payouts API create batch, batch-status lookup, webhook signature verification and payment ledger.
- Duplicate-payout safeguards and explicit, status-aware retries; no blind retry loop.
- SQLite persistence in `server/data/pr2pay.sqlite`.
- Local PIN-protected moderator session.

## Requirements

- Node.js 20.19+ (Node 22.12+ or Node 24 recommended).
- An OpenAI API key.
- A PayPal Developer REST app with Payouts access. Start in Sandbox.
- GitHub access to the configured repository. Public repositories can be read without a token; private repositories need a fine-grained, read-only token with Repository permissions for Metadata (read), Issues (read), Pull requests (read), and Checks (read).

## Windows setup

1. Extract the `PR2PAY` folder somewhere convenient.
2. Open the folder in VS Code.
3. Copy `.env.example` to `.env`.
4. Open `.env`. The local demo PIN defaults to `246810`; change it and replace `SESSION_SECRET` with a long random value before sharing or exposing the app. Add your OpenAI key and PayPal Sandbox Client ID and Secret when ready.
5. Open a terminal in the project folder and run:

   ```powershell
   npm install
   npm run dev
   ```

6. Open `http://127.0.0.1:5173`. The API runs at `http://127.0.0.1:8787`.
7. Log in with the `MODERATOR_PIN` value from `.env`.
8. Open Settings and click **Verify and connect repository**. The repository URL is prefilled. PRs must target the configured `latest_version` branch.

For a single-process local run after building the frontend:

```powershell
npm run build
npm start
```

Then open `http://127.0.0.1:8787`.

There is also a `start-pr2pay.bat` helper that copies the example environment file if needed, installs dependencies if needed, builds the frontend, and starts the server.

## Configure a task in GitHub

Create an **open GitHub Issue** in the connected repository. Put the reward line near the very top (within the first eight lines) using this exact format:

```md
Reward: 25.00 USD

## Task
Implement the requested feature.

## Acceptance Criteria
- [ ] Validate the user input.
- [ ] Persist the result correctly.
- [ ] Add tests for the expected behavior.
```

The reward format is `Reward: amount CURRENCY`. This build accepts USD, EUR, GBP, CAD, AUD, JPY, SGD, HKD, CHF and NZD. Amounts are parsed and validated by the backend, not generated by the LLM. The reward saved at import time is an immutable snapshot used for that task's payout. Re-importing the same Issue does not overwrite it; create a new Issue if you need a different reward after import.

Acceptance criteria must be explicit checklist entries (`- [ ] ...`) or bullets under an `## Acceptance Criteria` / `## Requirements` heading. Keep the list to 25 or fewer criteria. A starter Issue body is included at `templates/github-task-issue.md`; copy its contents into an Issue in your repository.

In PR2PAY, open **Tasks & rewards**, paste the Issue URL and import it.

## Submit and review a Pull Request

1. A contributor opens a PR in the connected repository targeting the configured branch (`latest_version`).
2. In **PR reviews**, choose the imported task, paste the PR URL, and enter the contributor's PayPal email.
3. Run AI verification. PR2PAY reads the PR title/body, head SHA, changed files and patches, plus available CI check information.
4. Review the model's evidence criterion by criterion.
5. If at least 60% of criteria pass, the report becomes eligible. Criteria have equal weight: 3 of 5 is exactly 60%. Inconclusive does not count as passed.
6. Click **Moderator approve**. The server checks that the PR head SHA has not changed.
7. Review the final payment confirmation and click **Confirm & send payout**. The server checks the SHA again and sends the fixed Issue reward to PayPal.

The AI cannot approve a PR, change the task reward, or initiate a payment. GitHub remains read-only: PR2PAY does not create PR comments, GitHub reviews, commits, labels, merges or issue updates.

## Configure PayPal Sandbox

1. Sign in to the PayPal Developer Dashboard and create or select a REST app.
2. Use that app's **Sandbox** Client ID and Secret in `.env`:

   ```dotenv
   PAYPAL_MODE=sandbox
   PAYPAL_CLIENT_ID=your_sandbox_client_id
   PAYPAL_CLIENT_SECRET=your_sandbox_client_secret
   ```

3. Confirm Payouts API access is available for the app/account. A REST app credential alone does not guarantee Payouts product access.
4. Use Sandbox recipient accounts and test payouts before switching to live mode.
5. To receive webhooks, expose the local webhook endpoint over HTTPS using a tunnel during development (for example, an approved HTTPS tunnel). Register this URL in the PayPal app:

   ```text
   https://YOUR-PUBLIC-HOST/api/paypal/webhook
   ```

6. Subscribe to the Payouts events you need, at minimum batch success, processing, denied, and item success/failed/blocked events. Save the Webhook ID in `.env`:

   ```dotenv
   PAYPAL_WEBHOOK_ID=your_webhook_id
   ```

7. Restart PR2PAY after editing `.env`.

PayPal docs:
- [PayPal Developer Resources](https://developer.paypal.com/developer-resources)
- [Create Payout Request](https://developer.paypal.com/api/payments.payouts-batch/v1/definitions/create_payout_request/)
- [Show Payout Batch Details](https://developer.paypal.com/api/payments.payouts-batch/v1/payouts-get/)
- [Payout Webhook Events](https://developer.paypal.com/payouts/webhooks/)
- [Integrate Webhooks and Verify Signatures](https://developer.paypal.com/api/rest/webhooks/rest/)

**Country and account eligibility:** PayPal product availability and live Payouts permissions are country/account dependent. Sandbox can demonstrate the integration, but do not assume an Indian merchant account can initiate live Payouts. Verify the actual account and hackathon credentials with PayPal before describing live transfer capability. This app defaults to Sandbox for that reason.

## Retry and duplicate-payment behavior

- PR2PAY saves a payment record before calling PayPal.
- Every request uses a stable `sender_batch_id`; PayPal documents duplicate prevention for the same sender batch ID for 30 days and says retrying an HTTP 5xx with the same ID is safe.
- If the payout is processing or completed, the app will not retry it.
- If PayPal reports a terminal denied/canceled payout, the moderator can explicitly retry after refreshing its status; the retry uses a new batch ID.
- If PayPal returns `USER_BUSINESS_ERROR` with an instruction to use a new sender batch ID, PR2PAY follows that instruction on the moderator-triggered retry.
- If the outcome is unknown and there is no payout batch ID, PR2PAY marks it for reconciliation and does not blindly create another payout.
- Webhook events are signature-verified and duplicate event IDs are ignored.

## Environment variables

| Variable | Purpose |
|---|---|
| `PORT` | Backend port (default `8787`) |
| `MODERATOR_PIN` | Local moderator login PIN |
| `SESSION_SECRET` | HMAC secret for moderator session cookie; use 32+ random characters |
| `COOKIE_SECURE` | Set `true` only when serving over HTTPS |
| `DEFAULT_GITHUB_REPO_URL` | Prefills the repository URL |
| `GITHUB_TOKEN` | Optional fine-grained read-only GitHub token |
| `OPENAI_API_KEY` | OpenAI API key for PR evaluation |
| `OPENAI_MODEL` | Model name (default `gpt-4.1-mini`) |
| `PAYPAL_MODE` | `sandbox` or `live` (default `sandbox`) |
| `PAYPAL_CLIENT_ID` | PayPal REST app Client ID |
| `PAYPAL_CLIENT_SECRET` | PayPal REST app Secret |
| `PAYPAL_WEBHOOK_ID` | Webhook ID used for signature verification |

Never commit `.env`, expose PayPal secrets to the browser, or put API credentials in GitHub.

## Local data and tests

SQLite data is stored in `server/data/pr2pay.sqlite`. Keep this directory backed up if you need the local review and payment ledger.

Run the included pure-logic tests with:

```powershell
npm test
```

The tests cover reward parsing, criteria extraction and repository/PR URL validation. The live GitHub, OpenAI and PayPal integrations require internet access and valid credentials to test end to end.

## API routes

All routes except health, auth, and PayPal webhook require the moderator session.

- `GET /api/health`
- `POST /api/auth/login`, `POST /api/auth/logout`, `GET /api/auth/me`
- `GET /api/repository`, `POST /api/repository`
- `GET /api/tasks`, `POST /api/tasks/import`
- `GET /api/evaluations`, `POST /api/evaluations`, `POST /api/evaluations/:id/approve`
- `GET /api/payments`, `POST /api/evaluations/:id/pay`
- `POST /api/payments/:id/refresh`, `POST /api/payments/:id/retry`
- `POST /api/paypal/webhook`
- `GET /api/overview`

## Scope boundaries

PR2PAY is a hackathon demonstrator, not an accounting or escrow platform. It does not escrow funds when a task is posted, automatically watch repositories, automatically retry ambiguous payments, or guarantee that GitHub/PayPal/OpenAI APIs are available. Moderator approval is required for each payout. The local moderator PIN is suitable for a controlled demo, not a public multi-user deployment without stronger identity and access management.
